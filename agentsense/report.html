一页看懂

这篇论文要解决的问题、它的方法，以及本工程复现到了哪一步。

问题：在预算内安排移动工作者去采集数据

城市被切成网格，时间被切成时段。每个 (x, y, t) 单元是一个「感知任务」。 每个工作者有固定起点、终点和可用时间窗，每移动一步都要付费。

目标是在预算内，让采集到的数据 数量多（Q，覆盖的不同单元数）且 分布均匀（E，层次化熵）。 两者互相拉扯 —— 这就是全部难点。

方法：不重排，而是在已有方案上迭代改

先用传统规划器排出一个可行方案 S₀，再让三个 LLM Agent 轮流加工：

  • Solver 改方案（唯一动手的）
  • Eval 用代码验算并给建议（数字不交给模型）
  • Memory 记录哪次改动有用，供下一轮参考

取得「可行 且 J > J_base」即停，最多 10 轮。

✦
核心结论：基线校准在 Small / Medium 已进入 ±5%，Large 仍偏低 5–8% 且无法通过调参消除； 真实 LLM 链路已完整跑通，AgentSense 的 SR 与 AIR 均优于单 Agent，但样本量（n=5 / n=2）不足以支撑强结论。

为跑通真实模型所做的方法修正

这些问题是 Mock 下看不到的。展开查看每一条的动机与做法。

7 条修正：从「模型必然失败」到「模型可用」
  1. 把 worker 约束注入 prompt。原始 Solver prompt 不含每个工作者的起终点与时间窗， 模型必然造出非法路径。现在由 workers_spec() 显式给出硬约束。
  2. 确定性可行性修复。repair.py 只修终点、时间戳、连续性等必要处， 保留模型给出的路线形状，避免像 DP 重规划那样把 LLM 的编辑整条抹掉 —— 这是最初 AIR ≈ 0 的直接原因。
  3. 单 Agent 对照的口径。原 refine_single() 仍会调用 Eval Agent， 不符合「一次调用」定义。现在严格只做一次 Solver 调用，评估全在本地完成，并用单测锁定调用次数。
  4. 建议必须可执行。advice.py 把「下一步」算成具体动作 （招募哪个 worker、重路由哪个 worker、指向哪些未覆盖格），否则模型倾向于「不改动」。
  5. 保留历史最佳可行解。循环可能因相邻轮次退化而覆盖已有提升， 现在返回 best-feasible，指标读取实际返回的解（RunRecord.final_override）。
  6. 扰动下的公平比较。worker_unavailable 会让基线引用已移除的工作者； 现在先在扰动后的实例上把基线修复为可行解，再算 J_base。成功判据也改为「合规 且 不劣于基线」。
  7. 失效引用容错。workers_spec / SolverAgent.propose / refine 都会清洗指向已移除 worker 的引用，否则抛 KeyError。
